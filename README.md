# QBotMobile — 手机端 QQ 机器人（官方开放平台）

在 Android 手机上 **24 小时运行 QQ 机器人**，同时把手机当作 **维护端**（看状态、看日志、改规则、手动发言）。

不使用任何第三方协议库（NapCat / Lagrange / Shamrock），也不需要 root、Termux 或 Xposed ——
走的是 **QQ 官方机器人开放平台**，纯 HTTPS + WebSocket，一个普通 App 的前台服务即可长期在线。

> 官方明确说明：WebSocket 模式「不依赖公网服务器部署，适合个人单机使用，需维护长连接」。
> 这正是手机端场景的正确选择。

---

## 一、为什么这样设计

| 需求 | 方案 | 理由 |
|---|---|---|
| 手机 24h 在线 | 官方 WebSocket 模式 + 前台服务 | 不需要公网 IP，也不需要 root |
| 数据存在手机里 | Room 存日志与规则，Keystore 存凭证 | 离线可用，换设备导出即走 |
| 手机当维护端 | Jetpack Compose 五页维护界面 | 状态、日志、规则、AI（记忆/人设）、设置一个 App 搞定 |
| 不想用 OpenClaw | 自己实现机器人逻辑 | OpenClaw 是官方提供的 AI Agent 接入服务，本项目走"原创机器人"路线 |

### 关于「第三方协议」的说明

第三方协议端（NapCat 等）功能更全，但属于非官方协议，存在封号风控风险。
本项目**刻意只支持官方开放平台**，换来的是零风控、零 root、长期稳定。这是有意取舍，不是遗漏。

## 二、安装（最简方式）

**仓库不带成品 APK，也不带签名密钥**（公开仓库泄露签名密钥等于把应用的身份交出去）。
两种获取方式：

**方式一：GitHub Actions 云构建（推荐，零本地环境）**

1. Fork 或 Clone 本仓库到自己的 GitHub；
2. 仓库页面 → **Actions** → 「Build APK」→ **Run workflow**；
3. 等 3-5 分钟，在运行记录底部的 **Artifacts** 里下载 `QBotMobile-release.zip`；
4. 想用自己的签名（与旧版本覆盖安装需一致）：仓库 **Settings → Secrets and variables → Actions**
   添加 `KEYSTORE_BASE64`（`base64 -w0 your.jks` 的输出）与 `STORE_PASSWORD` / `KEY_ALIAS` / `KEY_PASSWORD`，
   下次构建会自动签名；不配则产出未签名包，需自行 `apksigner` 签名后才能安装。

**方式二：本地构建**

```bash
./gradlew assembleRelease        # 需要 JDK 17 + Android SDK 35
                                   # 产物在 app/build/outputs/apk/release/
```

要求：JDK 17、Android SDK（platforms;android-35、build-tools;34.0.0+），最低支持 **Android 8.0（API 26）**。

装完打开 → **设置** 页填入 AppID 与 AppSecret → 保存 → 回 **状态** 页点「启动机器人」。
想用 AI 就在 **设置 → AI 接入** 里填服务地址 + API Key + 模型名，点「测试连接」验证通过后保存。
**「AI」页**管理记忆（谁是谁、记住了什么）和人设（对不同人/群说不同的话）。

### 申请机器人凭证

1. 打开 [QQ 开放平台](https://q.qq.com/#/apps) 注册并完成**主体认证**（个人开发者需实名）。
2. 创建机器人，在管理端拿到 **AppID** 和 **AppSecret**。
3. 开发设置里把「事件订阅与回调方式」切换为 **WebSocket**。
4. 服务范围：未认证时机器人仅管理员可用，可添加到**你作为群主**的群里测试。

## 三、项目结构

```
QBotMobile/
├── botcore/                纯 Kotlin/JVM 协议层（不依赖 Android，可独立测试）
│   └── src/main/kotlin/com/qbot/core/
│       ├── auth/           AccessToken 获取、缓存、提前刷新
│       ├── api/            OpenAPI 封装（发消息、撤回、取网关）
│       ├── gateway/        WebSocket 网关状态机 + 重连退避
│       ├── engine/         规则引擎、运行时、日志
│       ├── ai/             AI 应答、缓存友好组装、记忆管线、人设解析、群感知
│       └── model/          协议报文与消息模型
├── app/                    Android 壳
│   └── src/main/kotlin/com/qbot/app/
│       ├── service/        BotForegroundService + ResurrectorJobService（保活）
│       ├── network/        NetworkMonitor（网络恢复监听）
│       ├── receiver/       BootReceiver（开机 / 升级后自启）
│       ├── runtime/        BotController（生命周期与依赖组装）
│       ├── data/           Room 数据库 + 加密设置仓库
│       └── ui/             Compose 维护端（状态 / 日志 / 规则 / AI / 设置）
```

**`botcore` 与 Android 解耦**是核心设计：协议层可以脱离模拟器直接跑测试，
将来也能搬到服务器或桌面端复用同一套引擎。

## 四、协议实现要点

```
取凭证 → 取网关 → 建连 → Hello(10) → Identify(2)/Resume(6) → READY(0)
                                   → 心跳(1) ⇄ ACK(11) → 断线退避重连 ↺
```

| 环节 | 接口 |
|---|---|
| 取凭证 | `POST https://bots.qq.com/app/getAppAccessToken` |
| 鉴权头 | `Authorization: QQBot {access_token}` |
| 取网关 | `GET https://api.sgroup.qq.com/gateway/bot` |
| 心跳周期 | Hello 下发，默认 45s |
| 断线续传 | `op6 Resume {session_id, seq}`，平台补发遗漏事件 |

### 针对 7x24 挂机做的加固

1. **心跳僵死检测**
   移动网络下 TCP 会进入"半开"状态——既不报错也收不到数据（Wi-Fi 切 4G、进电梯、NAT 老化）。
   如果只看心跳是否发出，机器人会"看起来在线"实则掉线数小时。
   因此额外监控 ACK 是否逾期，超过 `心跳周期 × 2.5` 即判定僵死并主动重连。

2. **带抖动的指数退避**
   `delay = min(1s × 2^n, 30s) × (1 ± 20%)`。抖动用于打散重连时刻，避免重连风暴。

3. **错误码分流**
   `4009` → Resume 保留会话；`4914`（已下架）/ `4915`（已封禁）→ 直接停机；
   其余 → 重新 Identify。**封禁时不再无意义地反复重连耗光电量。**

4. **Intents 四级降级**
   Identify 被服务端拒绝（关闭码 4013/4014 或 op9 Invalid Session）时，
   按 `完整订阅 → 去掉群成员事件位 → 仅消息事件 → 基础事件` 逐级降级重连，
   尽量保住「群@/单聊」能力；全部被拒才停机并提示去平台申请权限，绝不无脑重连。

5. **连接纪元（epoch）**
   每次新建连接递增，所有异步回调先校验纪元再处理，避免旧连接的迟到回调污染新连接状态。

6. **凭证提前刷新**
   凭证寿命 7200 秒，提前 5 分钟换新；OpenAPI 返回 401 时立即作废并重试一次。

7. **网关地址缓存 + 限频冷静期**
   `GET /gateway/bot` 限频严格，取到地址即缓存复用；万一触发限频，
   重连间隔自动拉长到分钟级（60-120s），不再秒级撞墙。

## 五、保活：这是最现实的一关

技术上机器人能跑，但**国产 ROM 会杀后台**。本项目做了多层保险：

| 层 | 机制 |
|---|---|
| 前台服务 | 常驻通知（用户可一键停止），`START_STICKY` 让进程被回收后系统尝试重建 |
| 定时复活 | `JobScheduler` 每 15 分钟唤醒一次，发现服务不在就重新拉起；`setPersisted(true)` 跨重启保留，进程整体被杀也能到点复活 |
| 开机自启 | `BootReceiver` 监听开机 / 升级广播（含华为等机型的 QUICKBOOT），顺带确保复活任务已注册 |
| 网络监听 | `ConnectivityManager.NetworkCallback` 动态监听，恢复后延迟 1.5s 重连 |
| WifiLock | `WIFI_MODE_FULL_HIGH_PERF`，避免系统在灭屏后限制 Wi-Fi 流量 |
| 重连 WakeLock | 进入重连流程的瞬间点亮的短超时（15s） WakeLock，保证退避等待到期后能立刻抢到 CPU 发包 |
| 看门狗 | 每 60s 校验，发现控制器停止且用户未主动停止则重新拉起 |
| 存活统计 | 记录「最近是谁把机器人拉起来的」（手动/开机/定时复活/系统重建），仪表盘可见——**复活次数持续上涨就说明 ROM 在杀你** |

> 注：Android 7.0 起静态注册的 `CONNECTIVITY_CHANGE` 广播不再回调，
> 因此**没有**在 Manifest 里声明网络广播接收器，改由服务内动态完成。

**你还需要手动做的两件事**（App 内有引导入口）：

1. 把本应用加入**电池优化白名单**（系统不允许应用自行豁免，必须用户在系统页确认）
2. 在系统设置里允许**自启动 / 后台运行**（MIUI、ColorOS、EMUI 位置各不相同）

仪表盘「ROM 保活指南」卡片按厂商给出了路径，并可一键跳转自启动管理页
（小米/华为/OPPO/vivo/三星，跳不动的机型退到应用详情页）。

做完这些，常规机型可稳定在线数天到数周；**但没有任何 App 能 100% 对抗国产 ROM 的
内存管理**——定时复活的意义就在于：即使被杀了，最多 15 分钟后它自己回来。

## 六、规则引擎

内置轻量自动回复，规则存本地数据库，**修改后无需重启机器人**（下一次消息即生效）。

- 匹配方式：`EXACT` 全等 / `CONTAINS` 包含 / `PREFIX` 前缀 / `REGEX` 正则
- 作用范围：`ALL` / `GROUP_ONLY` / `PRIVATE_ONLY`
- 优先级：数值越大越优先，命中后即停止匹配
- 回复变量：`{content}` 用户原话、`{sender}` 发送者、`{target}` 群/用户、`{time}` 时间、`{nl}` 换行

正则非法时会被安全跳过（不会导致崩溃）。

## 六·补、AI 接入

在「设置 → AI 接入」里填三项即可对话，走 **OpenAI 兼容协议**，一套配置通吃：

| 服务 | 地址 | 模型示例 |
|---|---|---|
| DeepSeek | `https://api.deepseek.com` | `deepseek-chat` |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode` | `qwen-plus` |
| Kimi | `https://api.moonshot.cn` | `moonshot-v1-8k` |
| 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-flash` |
| OpenAI | `https://api.openai.com` | `gpt-4o-mini` |
| 本地 Ollama | `http://电脑IP:11434` | `qwen2.5` |

- **地址容错**：填 `https://api.deepseek.com`、带 `/v1` 或完整路径都能识别，不会因为差一个 `/v1` 就 404
- **API Key 加密存储**（Android Keystore），与机器人凭证同一套加密方案
- **三种触发方式**：
  - `规则优先`（默认）：本地规则未命中才问 AI，关键词与 AI 混用
  - `AI 优先`：所有消息都走 AI，本地规则暂时失效
  - `仅 /ai`：只有 `/ai 开头`的消息才触发，其余按规则处理
- **多轮上下文**：按**人**隔离记忆（同一个群里 A 和 B 的历史互不串台），默认保留最近 6 轮，重启不丢失（Room 落库）
- **失败兜底**：AI 出错时按配置的话术回复（如"AI 暂时无法回答"），留空则不回复
- **清空上下文**：发送 `/ai 清空`（或 `新对话`）重置当前会话记忆
- **保存即生效**，无需重启机器人；「测试连接」按钮可在群里来消息前先验证 Key 是否正确

常见错误码已翻译成中文：401 → Key 无效、404 → 地址或模型名不存在、429 → 频率超限或额度不足。

### 响应速度与成本控制（1.2.2 起）

| 功能 | 说明 |
|---|---|
| **思考模式开关** | DeepSeek **默认开启思考**（先输出思维链再作答），这是"感觉慢"的主因。设置页默认**关闭**，关闭后请求体带 `{"thinking":{"type":"disabled"}}` 直接出答案；该参数仅对 DeepSeek 端点发送（OpenAI 等严格服务商遇未知字段会 400） |
| **提示词 token 可见** | 系统提示词输入框下方实时显示估算 token 数，超 1500 变红警示——提示词每轮全量发送，越长越贵越慢 |
| **上下文 token 预算** | 滑块控制「提示词 + 历史 + 本轮问题」总量上限（默认 3000）。超限时从最早的对话**成对丢弃**；服务端仍报超限（400 context length）会自动砍半重试一次 |
| **缓存友好组装** | system 提示词固定最前、内容逐字节稳定、历史只追加不重写。DeepSeek 前缀缓存要求「从第 0 个 token 起完全相同」，命中部分价格仅 1/10，首字延迟大幅降低（128K 场景实测 13s → 500ms） |
| **用量与命中率** | 仪表盘 AI 卡片显示最近一次请求的 token 总数、缓存命中率、回复 token；命中率长期为 0 说明提示词被动态内容污染，值得排查 |

## 六·补二、记忆系统（1.3 起）

机器人不只是"会聊天"——它**认识群里的每一个人**，并按人组织记忆。

### 身份识别：群聊里谁在说话

QQ 官方开放平台**不提供群成员昵称查询接口**，所以展示名按优先级从三个渠道获得：

| 优先级 | 来源 | 说明 |
|---|---|---|
| 3（最高） | 维护端手动备注 | 「AI」Tab → 记忆 → 点人名改名，永不被覆盖 |
| 2 | 用户自称 | 对机器人说「叫我 XX」自动学习 |
| 1（最低） | 平台自带昵称 | 事件 payload 里的昵称（部分事件才有） |

低优先级永远不能覆盖高优先级；日志与 AI 看到的都是**展示名**而非一长串 openid。

### 三层记忆结构

| 层 | 内容 | 作用域 |
|---|---|---|
| 工作记忆 | 与每个人的最近 N 轮对话原文 | **按人隔离**（群聊里 A 的历史不会进 B 的上下文） |
| 群聊背景 | 群里最近的消息摘要（含他人发言） | **按群共享**——这样机器人能理解「那他呢」这类跨人指代 |
| 长期事实 | 从对话中抽取的个人信息（喜好、身份、约定） | 按人存储，每人默认上限 50 条，超出按时间淘汰 |

组装请求时严格按 `人设(system) → 事实(system) → 群背景(system) → 历史(对话) → [展示名] 问题(user)`
的顺序拼接——system 部分逐字节稳定，DeepSeek 前缀缓存命中率才有保障。

### 用户侧指令（在群里直接对机器人说）

- `叫我 XX` —— 设置/更新在该群的展示名
- `我的记忆` —— 查看机器人记住了你的哪些事
- `忘掉 XX` —— 删除某条事实；`忘掉全部` 清空你的一切记忆（历史与事实都清）

这些指令的**执行**在本地完成（改名片、删记忆都是数据库操作），
**回复**则由 AI 按人设语气生成（见「指令回复的人设化」），不再使用固定句式。

维护端在 **「AI」Tab → 记忆** 里可以：看每个人记住了什么、手动改名、删除单条事实、
一键"忘掉全部"，以及总开关 / 每人条数 / 群背景大小 / 指令人设化等配置。

## 六·补三、人设系统（1.3 起）

同一台手机上的机器人可以**对不同人、不同群说不同的话**：

| 作用域 | 优先级 | 典型用途 |
|---|---|---|
| 按人 | 3（最高） | 对管理员用严谨口吻，对常聊的群友用吐槽口吻 |
| 按群 | 2 | 工作群严谨、水友群放飞 |
| 全局 | 1（兜底） | 默认人设，就是「AI 接入」里的系统提示词 |

人设条目在 **「AI」Tab → 人设** 里增删，可绑定到具体的人（从"最近互动的人"里选）或具体的群。
解析顺序：先看有没有按人绑定的，再看按群，最后回落到全局——完全没配人设时行为与旧版一致。

人设提示词与记忆事实**分开存放**：人设只影响语气与立场，事实只影响"知道什么"，
两者互不覆盖。

## 六·补四、群感知（1.4 起）

机器人在群里不只回答被 @ 的消息——它**尽量记住这个群本身**：
群里有谁跟它打过招呼、它自己在这个群叫什么、大家聊天的氛围。

### 平台限制与近似方案（先说清楚）

QQ 官方开放平台对群聊有**硬限制**，没有任何接口能拉取完整成员名单或群资料：

| 想知道 | 平台提供 | 本项目的做法 |
|---|---|---|
| 群成员名单 | ❌ 无接口 | 靠 `GROUP_MEMBER_ADD` 事件 + 每条 @ 消息累计「见过的人」，上限 500/群 |
| 群名称/群主 | ❌ 无接口 | 不存群名，用 openid 尾段标识；维护端可手动备注群名片 |
| 机器人自己的群昵称 | ❌ 无设置接口 | 聊天指令「叫你XX」+ 维护端手动设置，按群独立保存 |
| 全部群消息 | ⚠️ 需**群主逐群授权** | 授权后走 `GROUP_MESSAGE_CREATE` + 三级漏斗决定是否接话（见六·补五） |

因此「群里有多少人」的回答口径是**"跟机器人有过交流的约 N 人"**，
AI 提示词里也明确要求它不要编造群成员姓名。

### 事件接入（v4 intents）

订阅位在原有基础上新增 `GROUP_MEMBER_EVENT`（`1<<24`，官方 wiki 有定义、
botpy SDK 尚未收录的位），加上已订阅的 `GROUP_AND_C2C_EVENT`（`1<<25`）里的
全套生命周期事件：

| 事件 | 行为 |
|---|---|
| `GROUP_ADD_ROBOT` | 群档案建档；按设置发一句加群问候语（默认关闭，主动消息耗配额） |
| `GROUP_DEL_ROBOT` | 标记该群档案为不活跃（保留历史，不删数据） |
| `GROUP_MEMBER_ADD` | 新成员 openid 记入「本群见过的人」 |
| `GROUP_MSG_RECEIVE / REJECT` | 群主对「接收所有消息」的授权/撤销（同时控制主动发言）；撤销后不再接话与问候 |
| `GROUP_AT_MESSAGE_CREATE` | 发送者记入见过的人 + 刷新活跃时间（不论走规则还是 AI） |

Identify 被拒时按四级阶梯降级：完整订阅 → 去掉群成员事件位 → 仅消息 → 基础事件。

### 群档案进 AI 上下文

回复每条 @ 消息时，群画像（本群昵称、见过多少人、主动消息权限）
注入到提示词的 system 段——位置在事实之后、动态群背景之前，
内容短且极少变化，前缀缓存友好。

### 用户侧指令

- `叫你 XX` —— 设置机器人在**当前群**的名片（仅群聊有效，单聊会礼貌拒绝）
- `你叫什么 / 你是谁` —— 优先回答本群名片，没设则用官方名字
- `群里都有谁 / 群里有多少人` —— 报数量 + 列出报过名字的人，并说明还有多少人没报名

维护端在 **「AI」Tab → 群组** 里可以：开关/编辑加群问候语、
查看每个群的档案与成员样本、手动改群名片、删除群档案。
数据随 Room v4 增量迁移落库（老用户的身份/事实/人设全部保留）。

## 六·补五、群聊参与（1.6 起）

前面所有的能力都有一个前提：**只有被 @ 时机器人才知道群里发生了什么**。
1.6 起可以打开「接收所有消息」，让机器人像群友一样旁听并**有选择地**接话。

### 门槛在群主，不在开发者后台

这一点很容易搞错：开关**不在** QQ 开放平台后台，而在 QQ 客户端里、**按群独立**：

> 群设置 → 群机器人 → 本机器人资料页 → 把「机器人可获取的群聊消息范围」
> 改成「**获取群内全部消息**」

- 只有群主/管理员能改，每个群要单独开一次；
- 开启后平台回调 `GROUP_MSG_RECEIVE`，关闭回调 `GROUP_MSG_REJECT`——
  这两个事件本来就在订阅里，因此本项目的群档案字段 `proactiveAllowed`
  同时就是"该群是否已授权"的标志；
- 部分机器人需要企业主体认证，资料页里才看得到这个选项；
- 没授权时行为与 1.5 完全一致：只回 @ 消息，不会报错。

### 三级漏斗：为什么不是每条都回

一个活跃群一天几千条消息，每条都问模型既贵又慢，还容易被群友嫌吵。
因此判断分三层，逐层收窄：

| 层级 | 判据 | 成本 |
|---|---|---|
| 1. 频率 | 冷却（默认 45 秒，可调到 **1 秒**；按 5 分钟消息量自适应：热群 ×2、冷场 ×0.6）、每小时默认 60 次（**可设 0 = 无上限**）、每天默认 400 次（同样支持 0 = 无上限） | 零 |
| 2. 内容 | 疑问句 +30、长度适中 +10、@别人 −20、单字/表情 −20，达到阈值（默认 25）才成为候选 | 零 |
| 3. AI 判断 | 候选再按概率抽样（默认 35%），然后问模型一句「需要你接话吗」（maxTokens=8，temperature=0） | 极小 |

被叫到**群名片名字**时直接跳到接话（仍受 5 秒最小间隔与配额约束）——
群友叫了不理，比多回一句更伤体验。

热群放慢、冷场加快，这就是"看聊天频率"；疑问句加分、@别人减分，
就是"看聊天内容"。

### 顺带变强的记忆

- 全量消息写进**群背景**，默认保留 **200 条**（注入提示词时仍只取 20 条，
  不撑爆预算）——机器人第一次能真正理解"刚才在聊什么"；
- 全量消息带 `author.username`，这是平台**唯一主动提供真实昵称**的场景，
  会按"平台昵称"优先级记进身份名录（不覆盖用户自称与人工备注），
  「群里都有谁」从此能报真名；
- 群里的普通发言也会参与事实抽取（纯正则，命中才落库）。

### 身份认知（1.7 起补强）

平台给的身份线索只有碎片，这一版把它们拼得更完整：

| 想知道 | 来源 | 处理 |
|---|---|---|
| 群里每个人叫什么 | `author.username`（全量消息）/ 「叫我X」/ 人工备注 | 按 人工 > 自称 > 平台 的优先级入库，注入提示词时只报真名 |
| 机器人在本群叫什么 | 群名片没有接口，但 @ 消息的 `mentions` 里可能带机器人自己的 username | 自动采纳为群名片；用户用「叫你X」或维护端设置过则永不覆盖 |
| 群里都有谁 | 事件累计 + 名字名录 | 群画像注入前 8 个真名 + "另有 N 位没报名"，并明确禁止编造 |
| 改名后还叫旧名字 | 历史对话里残留旧称呼 | 每轮提示词都声明"对方现在的名字是 X，以此为准；旧称呼一律作废" |

维护端「AI Tab → 群组」里每个群的成员样本会显示学到的昵称，
没学到的显示「群友 + openid 尾号」，不会再是一串纯编号。

### 成本与安全

- 参与默认**关闭**；关闭时全量消息只记记忆、不发言；
- 「插话前让 AI 判断」可以关掉，只保留规则 + 概率，零额外模型调用；
- 群主撤销授权（`GROUP_MSG_REJECT`）后立即停止接话；
- 回复走被动回复（带原消息 id），不消耗主动消息配额。

设置位置：**「AI」Tab → 群组 → 群聊参与**。

### 两级消息链路（1.7.1 起区分得更清楚）

机器人收到的群消息只有两类，处理方式完全不同：

| 类型 | 判定 | 处理 | 是否可能不回 |
|---|---|---|---|
| **@ 我的消息** | `GROUP_AT_MESSAGE_CREATE`，或全量消息的 `mentions` 含机器人 | 永远走完整回复链路（指令 → 规则 → AI） | 否 |
| **普通消息** | `GROUP_MESSAGE_CREATE` 且没有 @ 机器人 | 只入库记忆，再由三级漏斗决定是否接话 | 是 |

判断只针对**普通消息**——@ 是明确的对话邀请，不该再让模型猜"要不要理"。

### 群消息查看器（1.7.1 起）

「AI」Tab → 群组 → 每个群右侧的「**消息**」：实时显示机器人**听到**的内容，
与它理解群氛围用的是同一份数据（群背景，最多 200 条）。

每条消息都带两样东西：

- **类型标签**：`＠我`（红色）或 `普通`；
- **处理结论**：`已接话（规则 40 分）` / `不接：冷却中（45 秒）` /
  `不接：概率未命中` / `不接：AI 判断不需要接话` / `不接：群聊参与未开启` /
  `@ 了机器人，交给 @ 链路`。

所以"它为什么不理我"不用再猜——打开这个列表就能看到是没收到、被冷却挡住、
概率没过，还是模型判断不该插嘴。

列表为空时的提示会直接列出排查步骤（授权 → 发几条非 @ 消息 → 刷新），
并提醒「记忆 → 共享群聊背景」必须保持开启。

### 收不到全量消息时（排障顺序，1.7.2 起）

「AI」Tab → 群组 顶部新增**接收诊断**卡片，直接显示两类事件的到达次数：

```
@我消息：12 条 · 普通群消息：0 条
```

**@ 有、普通为 0 → 问题一定在平台侧，跟接话策略无关。** 按顺序检查：

0. **开放平台 → 开发设置 → 事件订阅与回调 → 接入方式必须选「WebSocket」**。
   选 Webhook 又没填回调地址时，平台会把事件推给一个不存在的地址，
   WebSocket 这边什么都收不到——这是最容易踩、也最难自己发现的一条；
1. 同一页的**接收事件配置**选「全部接收」；
2. **QQ 群设置 → 群机器人 → 本机器人资料页** → 「机器人可获取的群聊消息范围」
   改成「获取群内全部消息」（按群独立，只有群主能改）；
3. **重连一次**（停止再启动机器人），让新的订阅生效；
4. 在日志里搜「首次收到事件类型：GROUP_MESSAGE_CREATE」——
   没有这一行就说明平台还没推，代码侧无需再动。

两类都收到后，普通消息才会进入「群聊参与」的三级漏斗。

## 六·补八、被指名冒犯时按人设反应（1.8.2 起）

之前「阿远你是傻B吗」会被三级漏斗判成"不该接"——因为它按"没 @ 你就别插嘴"的
通用规则打分。但**被指名辱骂是例外**：装没看见比回错更伤人设。

### 冒犯检测（规则层，永远生效）

- **指名**：消息里出现机器人全名或名字后缀（"过去的阿远" → "阿远"）；
- **冒犯**：命中侮辱词表（含 sb / 沙比 等常见谐音缩写）；
- 两者**同时**成立才触发——"阿远今天没来"不会炸出来，
  "这游戏真垃圾"这种没名字的脏话也不会；
- 触发后**强制接话**（跳过概率与 AI 判断），只保留最小间隔防对骂刷屏；
- **@ 了别的群友**的消息直接让路：那是两个人的对话，再热闹也不插嘴。

### 反应与人设联动（提示词层）

触发时给模型注入一段"反应许可"：

> 刚刚「某某」当众骂了你：「原话」。这不是旁听，是冲你来的，必须按你的人设做出反应：
> 脾气暴躁的人设可以直接怼回去，阴阳怪气的人设可以冷嘲，温和的人设也可以冷处理。
> 你对「某某」的了解：……。熟人开玩笑和陌生人挑衅，反应程度应当不一样。
> 底线：不攻击家人、不威胁、不连续对骂，一两句到位即可。

所以「脾气不好被骂了骂回去」这类设定，只要写进人设（设置 → 人设）就会真正生效；
不同的人骂，反应也不同——模型会参考关于这个人的记忆事实。

### @ 链路同样生效

@ 机器人并带侮辱词（"你个傻逼"）时，@ 链路的回复也会带上"你刚被骂了"的上下文。

## 六·补七、群内指代与引用（1.8 起）

群里最常见的误解是「**他在骂谁**」。截图里那句「这个人是傻B」被机器人当成了骂自己，
根因不是"没读到全局消息"，而是缺三样东西：指代规则、被引用原文、对"我只看得到一部分"的自觉。

### 1. 群聊常识写进提示词

群聊场景下每条请求都会带一段固定规则（与人设无关，不受人设改写影响）：

> 消息里的「你」才指你；「他/她/这个人/那人/楼上/某人」通常指第三方，不要往自己身上套。
> 你只能看到 @ 你的消息（以及群主授权后的普通消息），看不到的部分不要编造；
> 对方指代不明时先问清楚，例如「说的是谁啊」。

### 2. 引用原文一起喂给模型

QQ 群里「回复某条消息」时平台会带 `reference_message_id`。现在会拿它去
200 条群背景里反查原文，注入成：

> 对方正在回复「阿远」的这条消息：我刚刚说什么了
> 判断「他/这个人/楼上」指的是谁时，优先看这条原文。

引用的原文只在**我们自己收到过**的消息里能查到；没收到的仍查不到——
但至少不会瞎猜。

### 3. @ 识别更宽容

- `mentions` 里比对 `id` / `member_openid` / `user_openid` / `union_openid` 四种字段；
- `<@...>` 剥离不再限定纯数字（openid 形态的 @ 也能剥干净）。

### 关于「程序里仿制全局消息」

**不可行，也不该做**。全局消息的唯一来源是平台推送；程序内"仿制"只能靠编造，
等于让模型凭空补上下文，幻觉会比现在严重得多。

可行的替代是**把已有的碎片拼成尽量完整的视野**：

| 碎片 | 来源 | 作用 |
|---|---|---|
| @ 我的消息 | `GROUP_AT_MESSAGE_CREATE` | 必须回的那部分 |
| 普通群消息 | `GROUP_MESSAGE_CREATE`（需两道开关） | 真正的群氛围 |
| 引用原文 | `reference_message_id` + 本地群背景 | 解决"他在说谁" |
| 群成员名册 | 事件累计 + 真实昵称 | 让模型知道"还有别人存在" |
| 明确声明"看不到" | 提示词固定规则 | 不确定时反问，而不是瞎猜 |

### 指令回复的人设化（1.5 起）

早期的指令回复是写死的固定句式（"你叫小明呀，我一直记得。"），
配上毒舌人设就是**人格分裂**。现在这些指令的回复分两层：

| 层 | 内容 | 触发条件 |
|---|---|---|
| 人设复述 | 指令结果作为**事实材料**连同人设提示词、记忆上下文交给 AI，让它用自己的语气说 | 复述开关开启（默认）且 AI 配置可用 |
| 固定句式兜底 | 此前的文案原样保留 | 复述开关关闭，或 AI 调用失败/返回空白 |

设计要点：

- **执行与表达分离**：改名片、删记忆等副作用仍在本地可靠完成，
  失败的只是"怎么说"，绝不影响指令功能本身；
- 给 AI 的事实材料是中性的（"对方的展示名是「小明」（对方自己告诉你的）"），
  并附任务说明：像本来就知道一样自然说出、不得编造关键信息；
- 会话历史只记录用户的原始话术，不记录「【指令结果】…」这类内部包装文本；
- 在 **「AI」Tab → 记忆 → 指令回复人设化** 可随时关掉，
  回到不消耗 API 的固定句式。

## 六·补六、人设进化（1.7 起）

写死的人设只会越来越不合身。现在可以让 AI 拿真实群聊当镜子，给自己改人设。

### 怎么工作

1. **触发**：人设卡片或全局提示词卡片上的「AI 优化」，可附一句额外要求
   （如"更毒舌一点，但别骂人"）；
2. **输入**：当前提示词 + 最近活跃群的 40 条群聊样本 + 额外要求；
3. **约束**：不换身份、不改价值观；删掉与样本冲突或空泛到无法执行的句子；
   补全口头禅、句子长度偏好与场景边界；
4. **校验**：输出 <20 字、>1500 字、或膨胀超过原文 1.6 倍 → 一律拒绝，保留原版；
5. **存档**：第一次优化前自动把当前版本存为「**初始版本**」（不可删除），
   之后每版都留快照（默认保留 20 条），可一键回滚。

> 为什么不做"每条消息后自动改人设"：人设频繁变动会让前缀缓存全部失效，
> 既慢又贵，模型也容易越改越飘。当前采用「手动触发 + 严格校验 + 可回滚」，
> 把进化频率交给用户判断。

设置位置：**「AI」Tab → 人设**（全局提示词与每条人设都有「AI 优化 / 版本历史」）。

  @ 消息永不走漏斗判断
- **群内指代**：群聊常识注入（「你」才指你、指代不明先问）、引用原文注入、

  改名后旧称呼作废声明
- **人设进化**：正常改写、代码围栏清理、过短/过度膨胀的输出被拒绝、样本进入请求体
- **BotRuntime 集成**：日志展示展示名而非 openid、记忆指令由 LLM 按人设复述、
  关闭复述开关走兜底文案、不同人的会话线程隔离但共享群聊背景、
  群事件经 onRawEvent 的端到端链路
- **网关集成测试**：用 MockWebServer 模拟平台，跑通 `建连 → Hello → Identify → READY → 事件分发`，
  并验证 `op7` 会触发自动重连、`op9`（Identify 被拒）会触发四级降级而非死循环
- **限频回归测试**：`/gateway/bot` 返回「接口调用超过频率限制」时进入冷静期，
  重连不再重复请求该接口（地址缓存复用）
- **Intents 降级测试**：完整订阅被拒 → 去掉群成员事件位 → 仅消息 → 基础事件逐级降级，全拒才停机并给平台指引

> 关于「连接中 / 鉴权中反复横跳」：真实故障的根因是 **Intents 位定义与官方不一致**
> （携带了服务端未定义的位），Identify 被拒后旧实现无脑重连形成死循环。
> 现已按官方 SDK（botpy）定义重写全部位，并增加三级降级；服务端拒绝的信号是
> **op9 消息**而非关闭码，两者都会触发降级。

> 关于「重连中 / HTTP 400 接口调用超过频率限制」：官方对 `GET /gateway/bot`
> 限频严格，早期版本每次重连都重新取地址，几十秒内就会打满频控并锁死在重连循环。
> 现已改为**取到地址即缓存复用**，只有握手被拒（401/403/404/410）才重新获取；
> 万一仍触发限频，会自动把重连间隔拉长到分钟级等待恢复。

## 八、已知限制

1. **机器人只能在其已被添加的群里工作**；单聊需用户主动发起（平台规则）。
2. **未认证机器人仅管理员可用**，且只能加入你作为群主的群。个人认证后上限 500 个群。
3. **主动消息有配额**，规则自动回复走"被动回复"通道不占配额，手动发送会占用。
4. **凭证不含群管理类高级能力**（如主动踢人、改群公告），如需请自行扩展 `OpenApi`。
5. **平台不提供群成员名单 / 群资料查询**，群感知只能靠事件累计近似：
   「见过的人」只覆盖与机器人有过交集的成员，每群上限 500 个样本。
   **未被 @ 的群消息默认收不到**，需要群主逐群授权「获取群内全部消息」；
   未授权时群氛围仍靠参与过的对话近似。
6. **AI 调用按 token 计费**，由你填写的服务商收取；群聊里 `AI 优先` 模式下每条消息都会请求，
   建议日常用「规则优先」或「仅 /ai」，需要时再切换。群聊参与额外产生少量判断调用
   （每条候选一次，`maxTokens=8`），可在设置里关闭「插话前让 AI 判断」。
7. `specialUse` 类型的前台服务在 Android 14+ 需要在 Manifest 声明用途（已配置），
   上架 Google Play 需要额外说明，自用无影响。

## 十一、路线图（规划中，尚未实现）

按依赖关系排序，前两项会先改消息处理管线，插件化放在管线定型之后。

### 1. 情绪值（短时状态）

- 每个群维护 `mood`（烦躁 ↔ 愉快，-1..1）与 `energy`（疲惫 ↔ 活跃，0..1）；
- 变化来源：被怼 / 被夸、话题冲突、连续被 @、长时间无互动带来的衰减；
- 注入方式：提示词里加一行「你现在有点烦，回复更短更冲」，
  **只调语气不改人设**，避免与人设进化互相干扰；
- 落点：`botcore/ai/MoodState.kt` + Room `group_mood` 表，与 `ChitchatPolicy`
  共用消息入口，避免重复遍历。

### 2. 好感度（长期关系）

- 按人维护 `affinity`（0..100）：互动频率、正向反馈、是否被帮助 / 被无视；
- 与情绪值分开：情绪是几十分钟的状态，好感是几周的关系；
- 影响：称呼亲疏、接话倾向（好感低时更冷淡）、主动搭话概率；
- 风险：要防止"讨好式漂移"。权重必须可解释，UI 里可查看与手动修正。

### 3. 网络热梗

- 方案 A（推荐）：手动导入「热梗包」（梗 + 含义 + 用法 + 例句），按周更新；
- 方案 B：定时抓热榜 → AI 提炼 10 条 → 入语料库；
- 注入时只给「最近可用的说法」一小块，并做冒犯性与时效过滤；
- 注意：抓取有版权与合规风险，默认不开启。

### 4. 插件化

- 现状：规则引擎、内置指令、AI 回复三条分支硬编码在 `BotRuntime`；
- 目标：`BotPlugin` 接口（`onMessage` / `onEvent` / `toolSpecs`）+ 注册表 + 事件总线；
- 形态：查天气、点歌、签到、抽卡等能力以插件热插拔，不碰主流程；
- 依赖：需要先把消息处理改成「管道 + 中间件」，情绪值与好感度会复用同一套钩子。
