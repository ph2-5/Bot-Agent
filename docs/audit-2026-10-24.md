## 一、人设之间的记忆隔离

### 现状矩阵

| 数据 | 存储 / key | 带 persona 维度 | 结论 |
|---|---|---|---|
| AI 会话历史 | `ai_messages`，key = `g:群:人\|personaId` | 是 | 隔离正常 |
| 人设设定 lore | `persona_lore`，`forPersona(personaId, groupId)` | 是 | 绑定错人格（见 A1） |
| 用户事实 facts | `facts`，按 `senderId` | 否 | 全局共享 |
| 群背景 | `room_messages`，key `g:群id` | 否 | 全局共享 |
| 私人线程 | `room_messages`，key `g:群id@p:人id` | 否 | 全局共享 |
| 群里的说法 slang | `slang_terms`，按群 | 否 | 按群共享 |
| 关系 / 好感 | `affinities`，按 `userId` | 否 | 全局共享 |
| 心情 / 表情包 | `bot_mood` / `meme_images` | 否 | 全局共享 |

证据：

- `botcore/src/main/kotlin/com/qbot/core/ai/Memory.kt:366-404`（`ConversationKeys`）
- `botcore/src/main/kotlin/com/qbot/core/ai/AiResponder.kt:347-351`（history key 叠加 persona）
- `app/src/main/kotlin/com/qbot/app/runtime/BotController.kt:257`（`personaIdProvider` 只取 active）
- `app/src/main/kotlin/com/qbot/app/runtime/BotController.kt:1838-1840`（history 取 `resolve(message)`）

### A1 人设设定绑错人格 · 中高

注入端用 `personaRepository.active()?.id`，提示词端用逐消息解析的 `resolve(message)`。
当某个群/某个人挂了覆盖层人设时，模型在扮演覆盖层角色，注入的却是激活档案的 lore。
两边不一致：历史按覆盖层隔离、设定按激活档案取。

修复方向：`RoomSocialStore` 的 `personaIdProvider` 改为接收 message 的解析结果，
与 `conversationScopeProvider` 同源。

### A2 群背景与私人线程不带人设 · 中

`ConversationKeys.room()` / `personThread()` 均不含 persona。切换档案后，新人格会读到旧人格的
assistant 消息，且被渲染成「你」（`AiResponder.kt:531-541`）。
会话历史干净、背景不干净，新人格会接着上一个人设的话茬说。

修复方向：给 key 或行加 persona 维度。涉及 DB 迁移，需先确认产品语义：
「换人设要不要断掉旧记忆」。

### A3 关系 / 好感跨人设继承 · 中

`affinities` 只有 `userId`。新人格一上来就带着旧人格攒的亲密度与芥蒂。

### A4 用户事实跨人设共享 · 设计取舍

`facts` 只有 `senderId`。若人设只换语气，这是优点；若是不同世界观角色，会串戏。

## 二、接话经验（chime lessons）的影响边界

### 数据流

```
消息
 ├─ 硬闸：@ / Forced → 直接接（不看经验）
 ├─ Skip → 直接不接（不看经验）
 └─ Candidate（仅当 chitchat.aiJudge = true）
      ├─ 读经验 lessonsForPrompt(groupId, maxInjectedLessons)   ← 经验只在这里进来
      ├─ 人设 + 关系 + addressee + 上次发言间隔
      └─ LLM 判定 YES/NO → 接
           └─ 回复生成（buildMessages）← 经验不在这里
```

证据：

- `botcore/src/main/kotlin/com/qbot/core/engine/BotRuntime.kt:528-573`
- `botcore/src/main/kotlin/com/qbot/core/ai/AiResponder.kt:654-657`（经验渲染进判定 prompt）
- `botcore/src/main/kotlin/com/qbot/core/ai/ChimeTraining.kt:303-323`（配额只在内存实现）

### 结论

- 经验**会**影响「是否接话」，但是**软提示**，不参与 `minScore` / `scoreWeights` 打分。
- **只在 `aiJudge = true` 时生效**；规则 + 概率抽样模式下完全不注入。
- **只影响「接不接」，不影响「怎么接」**：回复生成链路没有 lessons。
- 优先级低于用户显式 `chimeRules`。

### B1 类别配额在生产路径未生效 · 中

`MAX_PER_CATEGORY_INJECTED = 3` 只在 `InMemoryChimeTrainer` 里实现（测试用）。
生产走 `RoomChimeTrainer → ChimeLessonDao.promptLessons`，SQL 直接 `LIMIT`，没有配额。
后果：8 条经验可能全是同一类场景，测试全绿但真机不一致。

修复方向：把配额下沉到 `RoomChimeLessonStore.promptLessons`，或让 DAO 返回更多再由仓储裁剪。

### B2 排序只涨不降 · 中

排序 `本群优先 → supportCount desc → updatedAt desc`，同类相近经验 `mergeInto` 会
`supportCount + 1`，但没有衰减/过期。一条错判经验被反复确认后会长期占据前排，
导致持续偏向 YES 或 NO（一直抢话 / 一直潜水），只能手动停用。

### B3 经验不区分人设 · 中

`chime_lessons` 无 persona 字段。甲人设学到的偏好会作用到乙人设，与判定提示词里的人格描述冲突。

### B4 hits 语义偏差 · 低

`hits` 是「被注入次数」而非「被采纳次数」，既不衡量质量，也不参与排序。

## 七、备份导入导出审计（第三轮）

### 已修

| 问题 | 处理 |
|---|---|
| 页面文案与实现相反：文案称「记忆事实、最近 200 条群聊」不导出，实际 v5 已导出 | 更新「数据与备份」页说明，明确长期记忆在备份内 |
| `version` 只写不读：更新版本备份被导入时静默丢字段 | 新增 `ConfigBackup.CURRENT_VERSION`，高于本机版本时在导入摘要首行提示 |
| 恢复 lore 只清全局设定，其他人格的旧梗 / 旧认识的人残留 | `LoreDao.clearAll()` 整表替换；旧备份 lore 为空时不动 |
| `growthCount` 导出但导入丢弃 | `PersonaDao.setGrowthCount` 恢复成长履历；游标 / 出生时间仍不恢复 |
| 重复导入同一份备份会让机器人发言与内心戏翻倍 | assistant 消息按「会话 + 时间 + 内容」、内心戏按「会话 + 人 + 时间 + 原话」去重 |
| 群档案只恢复 `botName`，在群状态与主动发言权限丢失 | 备份升到 v6，带 `active` / `proactiveAllowed` / `joinedAt` / `lastSeenAt`；旧备份这些字段为 null 时沿用本机值，活跃时间取较新者 |

### 有意不导（保持）

运行日志（3 天过期）、接话决策日志（7 天过期）、AI 会话历史、人格版本快照、群成员活跃度。
理由都是短周期运行态：搬过去只会把过期状态一起带过去。

### 已知边界

- 导入不是单一事务（DataStore 与 Room 混写），极端情况下会部分成功；导入摘要逐项汇报实际写入数。
- 最近对话是全局 2000 条而非「每群 200 条」，群特别多时会向活跃群倾斜。

### 结论：不单独做「数据导入导出」

换机后无法重新积累的数据（人格、设定、风格、经验、关系、梗、事实、最近对话、内心戏）已经全部在配置备份里；
剩下的都是短期运行数据，没有回灌价值。若确有排障 / 取证需求，应做「诊断包」——只导出、不导入：
日志 + 最近决策 + AI 会话历史 + 版本信息。跑一遍包，比设计一套双向数据迁移更直接。

## 八、多机器人并发运行（第四轮）

需求：在 QQ 开放平台申请了多个机器人，希望一个 App 内统一管理并同时在线。

### 架构决策

| 决策 | 理由 |
|---|---|
| 每个机器人一个独立数据库文件（`qbot.db` / `qbot-<id>.db`） | 人格、记忆、群档案、日志天然隔离，不必给 19 张表加 `botId`，也没有迁移风险 |
| 每个机器人一个 DataStore（`settings` / `settings_<id>`）与加密凭证（`qbot_secrets` / `qbot_secrets_<id>`） | 凭证各自加密，互不可见 |
| 默认机器人沿用历史文件名 | 老用户升级后人格与记忆原样可用，零迁移 |
| 一个前台服务承载 N 个 `BotController` | 通知只有一条，聚合为「x/N 个机器人在线」；省电、省内存 |
| 看门狗逐个 `reviveOffline()` | 某一个掉线不影响其他 |
| 服务未运行时改启用开关只落配置 | 避免没有前台服务时偷偷连网被系统判为后台滥用 |

### 实现

- 新增 `BotRegistry`：账号目录（名称 / 启用 / 创建时间），`migrateLegacyIfEmpty` 把历史单机器人收编为默认机器人。
- 新增 `BotManager`：`BotInstance`（account + settings + database + controller）、增删改、`startAll` / `stopAll` / `restartAll` / `restartBot` / `reviveOffline` / `anyAutoStart`、状态聚合 `statuses`。
- `BotApplication` 的 `settings` / `database` / `controller` 改为「当前机器人」的 getter，维护端代码无需改写。
- `MainScreen` 用 `key(currentBotId)` 重建整棵子树，切换机器人后所有页面的 `remember` 状态与数据源同步切换；账号多于 1 个时顶部常驻切换条。
- 新增「机器人管理」页（`BotManagePage`）：新增 / 重命名 / 启用停用 / 删除 / 设为当前；删除会连带删除该机器人的库与凭证，且至少保留一个。
- 「机器人凭证」页改为维护当前机器人，保存后只重连该机器人。
- 备份页只备份当前机器人，导出文件名带上机器人名称，页面明确提示逐个切换导出。

### 有意不做

- **不做跨机器人共享学习成果**：同群两个机器人共享记忆会让人格串味，与「每个机器人是独立角色」的定位冲突。
- **不做「一个机器人多个 AppID 轮换」**：QQ 开放平台的 AppID 就是机器人身份，不是同一身份的凭证池。

## 九、名字被提及 ≠ 被叫（第五轮）

真实群聊暴露的连锁问题：两个群友互相玩梗拌嘴，机器人插话「你少来，我爹没这么欠」，
被回「我和陈泽说话关你阿远什么事」后继续回「骂人就关我事」，最后对方不得不澄清「我不是阿远。认错人了。」

### 根因（三处规则都只看字面）

| 环节 | 旧行为 | 后果 |
|---|---|---|
| `ChitchatPolicy` 的「叫名字必答」 | 名字任意位置出现即 `Forced` | 「关你阿远什么事」里名字被夹在中间，越被推开越要接 |
| `InsultDetector.targetsBot` | 名字出现 + 句中有「你」即算指名冒犯 | 划界句被判成辱骂，触发「必须回嘴」 |
| `AddresseeDetector` | 没有「两人对话」概念，一律判全群 | 复盘显示「对全群说」，回复也按全群口吻写 |

### 修复

- `BotNameMatcher` 新增 `called`（称呼）与 `mentioned`（提及）两个层级：
  - `REFUSAL_PATTERNS`：关你什么事 / 不关你事 / 没跟你说话 / 别插嘴 / 一边去 等明确划界；
  - `NEGATED_NAME_PATTERNS`：我不是X / 别喊X / X今天没来 等否定与澄清；
  - 模板存 `String` 而非 `Regex`（`{{name}}` 进 `Regex` 会在类初始化时抛异常）。
- `ChitchatPolicy`：划界判定**优先于**冒犯回应——对方明确不要你说话时，宁可闭嘴也不回嘴。
- `InsultDetector.targetsBot`：改用 `called` 并前置划界判断，划界句不再算冒犯。
- `AddresseeDetector` 新增两人对话判定：窗口内无机器人发言、只出现两个发送者、最后 3 条都在这两人之间 → 判为 `MEMBER`。
- 提示词双保险：判断提示词增加「不站队劝架 / 划界不是邀请 / 名字被提及不等于叫你」；群画像增加「名字只指你自己」「玩梗只当玩笑，不认亲也不自称是谁的爹」。

### 设计取舍

- 规则层只认确定的划界与否定表达，**宁可漏判交给 AI 判断，也不误判成「被叫」**。
- 两人对话判定要求「无机器人发言」：机器人一开口就不再算两人局，避免刚被叫完就判成插话。
- 只改判定与提示词，不新增开关：这是纠错而非新功能，用户不需要理解一个「是否允许玩梗」的配置。

## 十、说话人与正文分离（第六轮）

反馈：模型引用前面几条消息时，似乎把「名字」当成消息内容的一部分，而不是说话人。

### 核查结论

不是错觉，但也不是某处直接把名字拼进了 `content`。存储层 `RoomMessage.senderName` 与 `content` 一直是分开的；
问题出在**渲染层**：所有注入点都自行拼成单行 `[名字] 内容`，而整块又是一个 system 消息。
当正文本身以人名、方括号或冒号开头时，模型没有结构信号区分"谁在说"和"说了什么"。
另外还有一处确定的归因错误：群背景里机器人自己的行 `senderName` 为 null，旧代码回退成 `[机器人]`，
模型会把它当成群里另一个 bot，而不是自己。

### 修复

| 位置 | 旧 | 新 |
|---|---|---|
| 群聊背景 / 按人对话 | `[小明] 内容`（单行） | 第一行 `[小明]`，第二行正文 |
| 机器人自己的行 | `[机器人] 内容` | `[你] 内容` |
| @ 机器人的消息 | 无标记 | `[小红 · @你]` |
| 本轮说话人 | 拼进 user 消息 `[小明] 问题` | 独立 system 块声明「这一轮跟你说话的人是「小明」」，user 消息只放原话 |
| 判断上下文 / 复盘片段 / 人设演化 / 人格成长 / 梗学习 | 各自拼单行 | 统一走 `TranscriptRender` |

块首统一附一句格式声明：第一行是元信息，第二行起才是正文。名字在结构上不再可能与内容混淆。

### 设计取舍

- 两行式只多一个换行，token 成本可忽略，但把"说话人归属"从语义推断变成了结构约束。
- 本轮说话人放到 system 块而不是 user 消息前缀：system 块保持连续，且 user 正文保持原话，便于历史与缓存对齐。
- 复盘页显示行数从 4 调到 6：两行一条，6 行仍能还原最近 3 条。

## 十一、记忆检索层（第七轮）

反馈：记忆不能只靠「上下文窗口 + 满了压缩」，希望做成可索引、可片段化搜索的结构，
先减少 token 消耗，再考虑用多个辅助 API 并行分析。

### 核查结论

- token 预算其实已经有了（`PromptAssembler` 的 30% / 25% / 20% 分段与降级顺序），
  上一轮讨论里说「没有预算」是错的。
- 但「按时间取最近 N 条」确实是瓶颈：旧事永远进不了提示词，
  而全量塞进去又会随记忆增长线性烧钱。
- FTS5 不能用：minSdk 26 对应 SQLite 3.18，FTS5 不保证编译，trigram 要 3.34+。

### 实现

| 层 | 内容 |
|---|---|
| 分词 | `MemoryTerms`：中文二元组 + 2..4 字短专名整词 + 英文整词；停用字过滤 |
| 索引 | `memory_terms` 表，主键 `(kind, refId, term)`，REPLACE 幂等；DB v16 迁移 |
| 检索 | `RoomMemorySearcher`：词条命中 → 按 `(kind, refId)` 归组 → 回查原文 |
| 打分 | `MemoryRanker`：稀有度（df）× 时间半衰期衰减 × 重要性 × 命中覆盖度 |
| 精排 | `LlmMemoryReranker`：可选第二套 API，只回编号，失败/空结果退回本地排序 |
| 注入 | 事实「命中优先 + 原顺序补齐」；群背景「最近 6 条硬保底 + 命中旧消息」 |
| 回退 | 开关关闭、索引未就绪、检索抛异常 → 自动回到旧路径，绝不因索引坏掉不回复 |

### 分层开关

- 索引开关（`searchEnabled`）：关掉后连索引写入都停，省 IO。
- 辅助 API 开关（`auxRankEnabled`）：与索引开关解耦，只影响是否调用第二套模型。
- 表层只给两个开关；topK / 半衰期 / 候选数收进「高级参数」展开，避免默认界面堆参数。
- 辅助模型地址/模型/Key 留空时沿用主模型配置，用户不必为「试试精排」再配一套凭证。

### 设计取舍

- 索引是派生物，**不进备份**；启动时按「索引表最大 refId」游标在后台回填，不重扫全部历史。
- 不做「多 API 分块并行读记忆」：全局判断任务被拆块后，各块会各自误判「该不该说」，
  最终汇总反而更慢且更不一致；只在检索链路上做串行精排。
- 中文二元组比整句 embedding 便宜、可解释、可增量更新；手机端记忆规模（几千条）不需要向量库。
- 上下文预算与单次生成上限同步调高（预算 1000..64000，输出 200..32000），
  由用户按模型窗口自行约束。

## 十二、图片链路：从 URL 引用到本地字节

### 问题

QQ 的图片地址是带签名、带防盗链的临时链接，通常几小时就失效。

- **收图**：图库只存 URL，当天捡的表情包第二天就是死链；
- **发送**：把 URL 交给平台去拉，链接一过期就上传失败，只能静默跳过；
- **看图**：同样是拿 URL 给视觉模型，失败率高；png/gif/webp 各接口兼容性也不一致。

根因是**把内容的生命周期外包给了平台的临时地址**。修法不是重试，而是把字节留在自己手里。

### 实现

| 链路 | 做法 |
|---|---|
| 收图 | 下载 → 解码 → 转 JPEG（最长边 1024、质量 85）→ 存 `files/memes/<sha1>.jpg` → 表里只存相对文件名；任一环节失败就不入库 |
| 发送 | `path` 非空 → 读本地文件 → `file_data` base64 直传（`file_type=1`、`srv_send_msg=false`）；`path` 为空 → 回退 URL 上传；都失败 → 只发文字 |
| 看图 | 下载后同样先转 JPEG 再内联 `data:` URL；转码失败退回原始字节 |
| 备份 | 只导 `path` 字段，不导图片文件；换机后文件不存在 → 读到 null 自动回退 URL，不报错 |

### 关键约束

- `file_data` 的值是**纯 base64**，不带 `data:image/...` 前缀；
- **5MB 是原始字节的硬限制**，base64 会再膨胀 33%，不能按编码后长度判断（超限在本地直接返回 null，不发请求）；
- GIF 只取第一帧——表情包动图转静态是可接受的损失，换来格式统一；
- 转码、读写盘全部在 IO 线程，不占消息处理线程；
- 目录按「文件数 200 / 总体积 50MB」双上限淘汰，按最久未用排序，用过的图会被摸时间戳留下。

### 兼容

- DB v16 → v17：`ALTER TABLE meme_images ADD COLUMN path TEXT`，老行 path 为 null，行为与升级前一致；
- 未注入 `ImageTranscoder` / `MemeReader` / `LocalImageStore` 时（测试、轻量模式）自动退化为原 URL 链路。

## 十三、从响应式到自主式：让状态驱动开口

### 问题

在此之前，机器人是纯响应式：消息进来 → 判断该不该回 → 回。它**没有自己的状态**。

`bot_mood`（情绪）、`affinities`（关系）、`inner_thoughts`（内心戏）、`chime_lessons`（插话经验）
这四份数据都已经存在，但只影响「回复时的语气」，不影响「要不要开口」。
结果是：机器人永远只在被叫时说话，哪怕它刚刚想过一句话、哪怕话题正撞在它的人设上。

### 设计

**两道闸门**——先本地算，再花钱问：

```
闸门一（0 API 成本）：drive = base × interest × mood × closeness × timing − interruptCost
    没素材（最近没对话、没有未说出的内心戏）直接 HELD
闸门二（一次便宜模型调用）：最近 6-10 条对话 + 内心戏 + 人格摘要 → SPEAK / HOLD + 理由 + 主题
两道都过，才用主模型生成正文
```

- `AutonomousDrive`（botcore，纯 JVM 纯函数）：打分规则写死，阈值来自 `DriveConfig`；
- `AutonomousGate`（botcore 接口）+ `LlmAutonomousGate`（app 实现）：复用记忆精排已有的 `AuxAiConfig`，不新建配置类型；
- 开口本身仍走 `BotRuntime.sendReply`，只是触发者从「有人叫」换成「它自己想说」——**没有第二条发送链路**。

**节拍器**（`AutonomousScheduler`，仿 `PersonaGrowthScheduler`）：

| 触发源 | 时机 | 作用 |
|---|---|---|
| 消息后顺带评估 | 每条群消息处理完，随机延迟 20-40 秒 | 主路径；立刻接话像反射，隔半分钟像想了想 |
| 定时 tick | 每 10 分钟 | 兜底；让「沉默一阵后接一句」成为可能 |

**忍住必须记账**：每次 HOLD 写 `autonomous_decisions`，带话题指纹（`MemoryTerms` 抽 4 个词，不按原文 hash，标点变一变仍算同一话题）。
同指纹 30 分钟内累计 HELD ≥3 次 → 该话题冷却，不再反复想同一句。

**不耗主动额度**：第一批全部走引用回复（带最近一条消息的 `msg_id`）。平台看来是「回复已有消息」，不计入主动消息额度；
只有「群里超过 5 分钟没人说话且 drive 极高」才需要真正的主动消息，本批不做，代码里留 `proactiveSend` 的 TODO。

### 三档模式（产品决策）

不是开/关二元，而是三档——「被叫才说」和「自己想插一句」本来就是两种行为：

| 档位 | 行为 | 对应版本 |
|---|---|---|
| OFF 纯响应 | 只在 @ / 叫名字 / 明确对话时回；chime 与 drive 全关 | 更保守 |
| **PASSIVE 被动参与（默认）** | 被叫必回 + 群里有明确话题时轻度插话；drive 不跑 | **= 2.11.x 现状** |
| ACTIVE 自主 | PASSIVE + drive 驱动的自主开口 | 本批新增 |

约束：

- **默认 PASSIVE**，老用户升级后行为零变化；
- ACTIVE 必须用户主动选；
- 支持按群覆盖（`group_behavior` 表）：全局一个默认档，个别群单独设，没设过的群回落全局；
- 切档立即生效（设置是 StateFlow，调度器每次评估都取最新值，不等 tick、不重启）；
- **OFF 档下 drive 完全不跑**（`evaluate` 第一行就返回），保证零额外消耗。

### 避坑

- **不和 chime 抢答**：`BotRuntime` 把 chime 成功的开口时间记进 `spokeAtMillis`，自主调度评估前先看 5 分钟内是否刚说过；
- 最后一条消息是发给自己的（`isAt`）→ 直接跳过，不抢被动回复；
- 失败静默：模型报错、超时、解析失败都只记一条 HELD + 日志，不影响正常回复；
- `inner_thoughts` 只取最近 3 条，且过滤到本群，不整段塞进提示词；
- 便宜模型调用每天上限 120 次，多机器人各自计数，决策表按 robot 独立库隔离。

### 数据

- DB v17 → v18：`bot_mood` 加 `lastSpokeAt` / `suppressedCount`；
- 新表 `autonomous_decisions`（`groupId` / `score` / `outcome` / `reason` / `fingerprint` / `createdAt`，7 天自动清理）；
- 新表 `group_behavior`（按群覆盖档位）。

### 未做（留给下一批）

消息后评估与 tick 都在「群里有近 30 分钟对话」时才有意义，所以 B 通道（群里完全安静时主动发起）没有做；
`proactiveSend` 接口与额度语义已在代码注释里标出位置。

## 十四、场景语境：从单条判定到跨消息意图

### 问题

两个机器人（或机器人与真人）想演一段双人对谈，能接一轮，**接不了第二轮**。

根因不是阈值，而是判定链**每句话独立评估**：

```
消息进来 → 是不是 @ 我？→ 是不是叫我名字？→ chime 打分够不够？→ 回 / 不回
```

三个机制同时会阻断对谈：

1. 对方 bot 不会 @ 你 → 不触发「必答」；
2. 对谈里大量台词不叫名字（「您给说说」「我呀」）→ 不触发「叫名字必答」；
3. 两个人在互聊 → `AddresseeDetector` 判为 `MEMBER` → chime 认为「别插话」。

而且 `IncomingMessage` **没有 bot 标识**（平台已给 `author.bot`，代码没解析），
系统分不清「这句是人说的还是另一个 bot 说的」。缺的是「我正在做一件事」这个状态。

### 设计：三层结构

```
第一层 · AI 决定策略（引导式）
  start_scene(role, partnerName, goal) / wait_for_reply(seconds)
  prompt_partner(message) / end_scene(reason)
第二层 · 代码执行机制
  scenes 表：谁在演、第几轮、等谁、等到什么时候
  判定链最前面接入：有场景 + 轮到我 → 跳过 chime 直接生成
  超时检查：消息驱动 + 15 秒定时巡检（不挂起等待）
第三层 · 代码守底线（AI 不可越界）
  单场景 10 分钟 / 单群每小时 30 条 / 等待 5-60 秒
  连续 3 次催场无回应 → 强制收尾
  人类插话 → 注入「有人插话」信号，不强制结束
```

原则：**AI 决定「做什么」，代码决定「最多能做什么」。**

### 判定链接入（关键改动）

`BotRuntime.sceneLook` 在现有判定之前查询本群进行中的场景：

| 情况 | 行为 |
|---|---|
| 无场景 / 开关 OFF | 返回 null，判定链与 2.12.0 **逐字节一致** |
| 等对方期间别人说话 | 只入群记忆，不生成（记 `lastActivityAt` + 插话者名字） |
| 对方接话 | `ChitchatGate.Forced("场景轮次：该我接")`，跳过 chime |
| 第三方插话 | 走原判定链（可能插话），并记下插话者供下一轮注入 |

场景块（`ScenePrompt`）插在人格与说话约束之后、记忆之前：它决定「这一轮该起什么作用」，
而记忆/关系照常注入——场景只改「要不要说」，不改「以什么身份说」。

**工具可见性**：`start_scene` 常驻但 OFF 时不发；`wait / prompt / end` 只在
「有进行中场景」或「最近 3 分钟结束过」时发给模型（OBSERVE 全发，用来观察误用）。

**引用回复**：催场必须有 `lastSentId`（自己上一条群消息 id）走被动回复，
拿不到 `msg_id` 或发送失败就直接收尾，不静默重试。

### 三档模式

| 档位 | 行为 |
|---|---|
| **OFF（默认）** | 场景功能完全关闭：工具不发给模型、判定链不查场景 |
| OBSERVE | 工具照常调用、决策照常落表，但 `executed=false`，不产生任何行为 |
| ACTIVE | 工具真正执行：等待、催场、收尾 |

OBSERVE 是第一期的主要交付形态——先看 AI 开场的时机准不准，再决定是否切 ACTIVE。
调试入口在「接话复盘」页：场景开关三档 + 当前群场景状态（轮次 / 等谁 / 剩余等待）+ 最近 20 条决策。

### 数据

- DB v18 → v19：新表 `scenes`（`kind` / `participantsJson` / `status` / `turnIndex` / `expectedSpeakerId` / `waitUntil` / …，索引 `groupId+status`）；
- 新表 `scene_decisions`（`action` / `argsJson` / `executed` / `reason` / `createdAt`，7 天自动清理）；
- `IncomingMessage` 新增 `senderIsBot`（解析 `author.bot` / `member.bot`）；
- 存储与工具都在 botcore（纯 JVM，可单测）；Room 实现由 app 注入，两个机器人各自一个库，场景状态天然独立。

### 避坑

- **不挂起等待**：`wait_for_reply` 只写 `waitUntil` 时间戳，靠下一条消息或 15 秒巡检推进，禁止 `delay(25000)`；
- **防工具滥用**：提示词明确写「不要为了用动作而用动作」，代码里同一场景相邻两轮不能连续 `wait_for_reply`；
- **OBSERVE 也落表**：否则无法复盘，这是第一期的主要价值；
- **人格不猜角色**：谁逗谁捧由 AI 按人格判断，代码不硬编码；
- **被动回复窗口**：催场发送失败一律转 ENDED，不重试。

### 待实测

本批只完成代码与自动检查（`:botcore:test` 全绿、`:app:compileDebugKotlin` 通过）。
「OBSERVE 模式真实群观察 2 小时、统计 AI 发起场景次数与合理性」需要真机与真实群，
沙箱内无法完成，留给发布后按以下口径采集：

- 记录 `scene_decisions` 中 `action=START` 的条数与每次的 `argsJson`（对手、目标）；
- 人工判定「这次开场是否真的在发起一段对谈」，统计误判率（目标 < 20%）；
- 同时确认 OBSERVE 期间群里**没有任何行为变化**（不出声、不等待、不催促）。

## 十五、场景契约：让 AI 自己写规则（第八轮）

> 任务书原文把这节编号写成「十四」，但「十四」已被 2.13.0 的场景语境占用，这里顺延为十五。

### 问题：固定模板只覆盖一种语境

2.13.0 的场景块是写死的相声模板（「你抛，对方接」「说到『底』就收」）。
一旦 AI 开的不是相声——比如两个机器人在群里演客服对骂、演老同学寒暄、演方言砍价——
它仍然会收到「你演逗哏」这一套，演出来的东西和语境对不上。

提示词里再加工种模板是走不通的：语境是无穷的，模板只能覆盖有限几种。
真正的解法是把「这次演出要遵守什么规则」交给进入场景的模型自己写，
代码只负责三件事：**让规则塞得进上下文、让规则在场景内不许变、让没有规则的老场景行为不变**。

### 数据结构

`SceneContract`（botcore，纯 JVM，可单测）：

| 字段 | 含义 | 上限 |
|---|---|---|
| `languageStyle` | 口音 / 语体 / 句长 / 怎么称呼对方 | 120 字 |
| `roleRules` | 角色名 → 该角色能做什么、不能做什么 | 4 个角色 × 80 字 |
| `taboos` | 禁忌 | 5 条 × 40 字 |
| `exitCriteria` | 什么情况算说完、怎么收尾 | 80 字 |
| `props` | 这次可以用的素材 / 话题（可选） | 3 条 × 40 字 |

- 所有上限在 `normalized()` 里**硬截断**（截断后补「…」，最终长度绝不超过上限），不是在提示词里请求；
- `fromJson()` 对畸形参数一律按类型取、取不到就丢，一次坏参数绝不打断开场；
- `isEmpty()` 会把「只有空白」也算成没写契约，调用方据此回退旧模板。

### 注入与渲染

`ScenePrompt.block()` 拆成两条路径：

- `contract != null && !isEmpty()` → `contractBlock()`：`[场景契约]`（语言风格 / 你的角色 / 对方 / 其他角色 / 禁忌 / 收尾 / 可用素材）+「契约在这个场景内保持不变，不要中途改写规则」+ 插话提示 + 动作块；
- 否则 → `legacyBlock()`：**与 2.13.0 逐字一致**（含 `对方演X。`、`这段的目标：`、`说到「底」…`）。

位置仍在人格之后、记忆之前（前缀稳定，能命中缓存）；契约**不进记忆、不进备份**，不写 `facts` / `lore` / ConfigBackup。
契约存在 `scenes.contractJson` 一列里，随场景一起读写；场景内不做 `update_contract`。

### 三处场景冲突（任务书 C1–C3）

| 编号 | 冲突 | 修法 |
|---|---|---|
| **C1** | 自主开口和场景抢话筒：正在演戏时它自己另起一句 | `AutonomousScheduler.evaluateLocked` 开头查**本群**：有进行中的场景 → 让位；刚结束不到 5 分钟（`SCENE_COOLDOWN_MILLIS`）→ 也让位。只查本群，A 群演戏不让 B 群闭嘴 |
| **C2** | OBSERVE 只读模式的数据被自主发言污染 | 两道闸门照常走完（保留观察价值），在真正发送前判断档位：`OBSERVE` → 记一条 `HELD`，`suppressedBy=SCENE_OBSERVE`，不发送 |
| **C3** | 场景档位是 per-bot 的，用户以为设一次两边都演 | 复盘页场景 chips 上方明说「场景档位按机器人独立设置。双人演出需要两个机器人分别设为 ACTIVE」 |

C1 的让位记录 `score=0.0`、理由写明「场景进行中/刚结束」，复盘时能看出是被场景压住的，不是模型判断错。

### 数据

- DB v19 → v20：`ALTER TABLE scenes ADD COLUMN contractJson TEXT`、`ALTER TABLE autonomous_decisions ADD COLUMN suppressedBy TEXT`；
- 两列都可空增量：老场景 `contractJson = null` → 回退固定模板；老决策 `suppressedBy = null` → 没被场景抑制过；
- `RoomSceneStore.save()` 写契约、`toModel()` 读契约（解析失败吞掉返回 null，不崩）；
- OBSERVE 不建场景，契约只存在 `scene_decisions.argsJson` 里——复盘页从最近一条 `START` 的 `argsJson` 里解出来展示（「最近一次『想开场』写的契约（未实际开场）」）。

### 避坑（实测 / 设计约束）

- **截断必须在代码里做**：模型不会老实遵守提示词字数，一段散文就能吃掉上下文；
- **契约位置固定**：放在人格后、记忆前，否则缓存失效、人格被规则污染；
- **不许中途改契约**：前后几句规则不一致，模型自己会精神分裂；
- **让位判断查「本群」**：按群查，不是全局；
- **OBSERVE 不能省判断**：C2 的修法是「照常评估、只不发送」，不是跳过评估——否则观察数据里看不出它本来想说什么。

### 自动检查

- `SceneContractTest`：超长截断到上限 / 空白项丢弃 / `isEmpty()` 判定 / 序列化往返（含中文与换行）/ 畸形参数不打断 / 老场景逐字回退 / 契约落到双方 / ACTIVE 落库 + OBSERVE 只进决策记录；
- `:botcore:test` 全绿；`:app:compileDebugKotlin` 通过；
- 沙箱无真机、无真实群，**OBSERVE 真实群观察记录（≥3 场契约原文 + 质量判断）留待发布后采集**，口径：
  - 从 `scene_decisions` 取 `action=START` 的 `argsJson.contract`，抄原文；
  - 逐条判断：是否具体到能照着做（出现「要自然」「要幽默」这类形容词即判为不合格）、角色规则是否区分了双方职责、收尾条件是否可执行；
  - 目标：不合格率 < 30%，否则收紧 `start_scene` 的描述与示例。

## 十六、向量记忆：语义召回与三层降级（第九轮）

### 为什么加、为什么可选

2.14.1 的检索是纯 bigram 倒排：问「上次聊的那个游戏」时，句子里的二元组一个都不在旧消息里，
**关键词匹配天然救不了同义改写**。embedding 正好补这一块。

但 embedding 有三个硬成本：要额外配一个服务商与 Key、每次检索多一次网络往返、失败会拖慢回复。
单机群聊机器人绝大多数时候用不上语义召回，因此这里的定位是**可选加分项**，
而不是把记忆系统改成向量库：

> 用户配了就用，没配就退回纯倒排——**默认行为一个字都不能变**。

### 三层降级

| 状态 | 行为 |
|---|---|
| 未配置 / 开关关闭 / 熔断中 | 纯倒排，`HybridMemorySearcher` 在调用向量前直接 `return base`，结果与 2.14.1 逐字节一致 |
| 已配置且调用正常 | 倒排结果 + 向量 TopN → RRF 融合（`k=60`）→ 交给原 `MemoryRanker` |
| 已配置但失败 / 超时 | 本次退回倒排并记日志；`EmbeddingGuard` 连续 3 次失败暂停向量检索 10 分钟，UI 显式提示 |

熔断与查询缓存都在 `EmbeddingGuard` 里：同一句话 60 秒内不重复调 embedding（LRU 64 条，按 model 隔离），
成功一次即清零失败计数。失败永远只是「这次没有向量加分」，不会让回复变慢超过一次超时（默认 8 秒）。

### 数据结构

`memory_vectors`（DB v20 → v21，纯增量建表）：

| 列 | 说明 |
|---|---|
| `kind` / `refId` / `model` | 联合主键；同一记忆重复向量化直接 REPLACE，回填幂等 |
| `dim` | 向量维度；由「测试连接」实际调用探测后写入，**不猜** |
| `scopeKey` | 检索范围（`g:群id` / `g:群id@p:人id` / `f:人id` / `p:人格id`），暴力检索时不用 join 源表 |
| `vec` | float32 小端，**入库时已 L2 归一化**，检索只做点积 |
| `createdAt` | 写入时间 |

`model` 必须存：换模型后新旧向量不可比，检索只读当前模型那一份，互不干扰。
`vec` 在 `EmbeddingVectors` 里用 `ByteBuffer.order(LITTLE_ENDIAN).asFloatBuffer()` 序列化。

### 入库链路

新增记忆只投递一条内存任务（`Channel`），后台串行调用，调用方绝不等待网络：

- FACT：事实原文；
- ROOM：滑动窗口 3 条 + 说话人（`小明：… \n 你：… \n 小红：…`）——单条「哈哈哈」的向量没有信息量；
- LORE：`名称：备注`；SLANG：`词：含义。用法：例句`。

少于 6 个字的文本直接跳过（`MIN_TEXT_CHARS`）。**LORE / SLANG 只入库、不进回复上下文**：
它们目前不参与检索注入，`MemoryKind` 扩到 4 类只是为「按语义找设定」预留，
`when (kind)` 在倒排与混合检索里都显式返回 null，行为与 2.14.1 一致。

### 检索与回填

- 混合检索：`Inverted.recall` 拿基线 → query 向量（带缓存）→ `memory_vectors` 按 `scopeKey + kind + model` 取候选
  → 点积 → 取 `max(limit×2, 16)` → 回查 facts / rooms → 倒排榜按稀有度排序、向量榜按相似度排序 → `Rrf.fuse`
  → 用 `(kind, refId)` 映射回候选（倒排也命中时以倒排那条为准，带词权重）；
- 维度不一致（换模型残留 / 探测错误）一律跳过，绝不越界；
- **scopeKey 过滤不能漏**：A 群的记忆不能召回给 B 群；
- 回填手动触发（`MemoryVectorBackfill`）：每批 20 条、批间隔 1 秒、退出页面即停，
  续跑靠 `NOT EXISTS memory_vectors` 查询，不碰 `ai_messages`。

### UI

设置 →「记忆系统」→「向量记忆」：

- 未开启且未展开时**整块折叠**，只有一行说明 + 「配置向量服务」；
- 展开后：服务商（硅基流动 / 智谱 / OpenAI / 自定义）→ 地址 → Key → 模型 → 维度（自动探测，只读）→
  「测试连接」→「已向量化 x / y 条 · 占用 zMB」→「开始向量化 / 停止」；
- 维度为 0 时开关打不开：提示「先测试连接」。探测失败不允许开启——维度错了，点积会全部被跳过，
  表面上开了实际一条都召回不到；
- API Key 复用现有 `qbot_secrets` 加密存储，不明文落 DataStore。

### 避坑

- **归一化必须在入库时做**，检索只做点积（省一次 sqrt，也不会因为忘归一化把分数算成余弦的倍数）；
- **`model` 字段必存**，否则换模型后新旧向量混在一起，分数没有意义；
- **维度不能猜**：预置服务商表里写了 `expectedDim`，但只作提示，最终以探测结果为准；
- **query 缓存**：60 秒窗口，避免同一句话在连续几轮里重复付费；
- **失败要静默降级**：embedding 挂了不能影响回复；
- **回填不要自动跑**：可能被限流、可能烧用户流量；
- **不要给 ai_messages 建向量**：那是「按人隔离的往返记录」，本身已经很短，语义检索收益低、写入量最大。

### 自动检查

- `EmbeddingSupportTest`（11 条）：L2 归一化后点积等于余弦（误差 < 1e-5）/ 零向量不产生 NaN /
  BLOB 小端往返 / 维度不同返回 0 不越界 / RRF 双榜靠前文档排第一 / RRF 截断确定性 /
  连续 3 次失败进入暂停且第 4 次不再调用 / 暂停到期自动恢复且成功清零 / 缓存按 model 隔离 /
  未探测维度时链路不就绪 / 端点归一化不重复拼 `v1`（本机地址默认 `http`，公网默认 `https`）；
- `:botcore:test` 全绿（584+ 用例）；`:app:compileDebugKotlin` 通过。

### 召回对比数据（发布后补采）

沙箱内**没有可用的 embedding 服务与 Key**（无法真实调用硅基流动 / 智谱 / OpenAI），
本节要求的「同一组 10 个 query，纯倒排 vs 混合检索各列 top3」**无法在这里真实采集**，
不做编造。发布后按以下口径补：

1. 在真机上导入一份真实群聊备份（≥ 500 条 room_messages + 50 条 facts），先建满倒排索引；
2. 准备 10 个 query，覆盖三类：①同义改写（「上次说的那个开放世界游戏」→ 原神 / 塞尔达）、
   ②专有名词（人名 / 群梗，验证倒排仍占优）、③时间承接（「前天他说的那件事」）；
3. 关闭向量记一次 `recallMemories` 结果，开启并回填后同样 10 个 query 再记一次；
4. 记录每个 query 的 top3（kind + 原文前 20 字 + 是否相关），统计：
   - 语义召回净增益（仅混合检索找回的相关条数）；
   - 倒排精度损失（融合后原本 top1 掉出 top3 的次数）；
5. 目标：语义类 query 净增益 ≥ 2 条，专名类 query 精度不下降；否则调 `Rrf.k` 或提高向量榜进入融合的门槛。
