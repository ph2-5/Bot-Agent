# 任务书：场景语境（Scene）与引导式驱动

> 目标版本：2.13.0（新能力）
> 前提：2.12.0 已合入（多机器人、自主开口、图片链路）
> 数据库：18 → 19
> 边界：第一期只做 **CROSSTALK（双人对谈/相声）** 一个场景 + **只读模式**

---

## 一、要解决什么

### 现象

两个机器人（或机器人与真人）想演一段双人对谈，能接一轮，**接不了第二轮**。

### 根因（已定位，不要重新猜）

现有判定链是**每句话独立评估**：

```
消息进来 → 是不是 @ 我？→ 是不是叫我名字？→ chime 打分够不够？→ 回 / 不回
```

三个机制同时会阻断对谈：

1. 对方 bot 不会 @ 你 → 不触发"必答"
2. 对谈里大量台词不叫名字（"您给说说""我呀"）→ 不触发"叫名字必答"
3. 两个人在互聊 → `AddresseeDetector` 判为 `MEMBER`（两人对话）→ chime 认为"别插话"

而且 `IncomingMessage` **没有 bot 标识**（平台已给 `author.bot`，代码没解析），系统分不清"这句是人说的还是另一个 bot 说的"。

**根本问题不是阈值，是缺少"我正在做一件事"的状态。**

### 目标

引入**场景（Scene）**作为跨消息的一等公民，让判定依据从「这条消息值不值得回」变成「我在哪个场景里、轮到我了吗、我该做什么」。

---

## 二、核心设计：三层结构

```
第一层 · AI 决定策略（引导式）
  每次生成回复时，通过 tool call 表达意图：
    · 开场  → start_scene(kind=crosstalk, role=comedian, partner=于谦, goal=...)
    · 等接  → wait_for_reply(seconds=25)
    · 催场  → prompt_partner("该您了")
    · 收底  → end_scene(reason="说到'底'了")

第二层 · 代码执行机制
  · scenes 表：谁在演、什么场景、第几轮、等谁、等到什么时候
  · 判定链最前面接入：有场景 + 轮到我 → 跳过 chime，直接生成
  · 超时检查：消息驱动 + 定时 tick（复用 AutonomousScheduler 节拍）

第三层 · 代码守底线（AI 不可越界）
  · 单场景最长 10 分钟
  · 单群每小时最多 30 条场景发言
  · wait_for_reply 参数上限 60 秒
  · 连续 3 次 prompt_partner 无回应 → 强制 end_scene
  · 人类插话 → 场景暂停（注入信号，不强制结束）
```

**原则：AI 决定"做什么"，代码决定"最多能做什么"。**

## 三、数据结构

### 3.1 Scene 模型（`botcore/.../ai/Scene.kt`，纯 JVM）

```kotlin
enum class SceneKind { CROSSTALK }

enum class SceneRole { COMEDIAN, STRAIGHT }   // 逗哏 / 捧哏

enum class SceneStatus { ACTIVE, WAITING, ENDED }

data class SceneParticipant(
    val senderId: String,
    val displayName: String,
    val isBot: Boolean,
    val role: SceneRole?,
)

data class Scene(
    val id: Long,
    val kind: SceneKind,
    val groupId: String,
    val participants: List<SceneParticipant>,
    val goal: String,
    val status: SceneStatus,
    val turnIndex: Int,
    val expectedSpeakerId: String?,
    val waitUntil: Long?,
    val lastActivityAt: Long,
    val createdAt: Long,
) {
    /** 我在这个场景里的角色 */
    fun roleOf(senderId: String): SceneRole?
    /** 现在轮到我了吗（expected 为空时视为轮到所有参与者） */
    fun isMyTurn(senderId: String): Boolean
    fun isExpired(now: Long, maxMillis: Long = 10 * 60_000L): Boolean
}
```

### 3.2 场景内提示词（`ScenePrompt`，纯 JVM）

生成时注入一个独立 system 块，位置在人格之后、记忆之前：

```
[当前场景]
你正在和「于谦」说相声（第 3 轮，你演逗哏）。
对方的定位是捧哏：你抛，他接。每句话都要给他留出接话的口子。
说到"底"（最后一个包袱抖完）就收，不要拖。

[可用动作]
你说完可以等他（wait_for_reply），他不接可以催（prompt_partner），
说到结尾就结束（end_scene）。不要为了用动作而用动作。
```

**要点**：动作说明必须加"不要为了用动作而用动作"——否则模型会每轮都调 `wait_for_reply`。

### 3.3 四个原语工具（`botcore/.../ai/SceneTools.kt`）

实现现有 `BotTool` 接口，注册进 `ToolRegistry`：

| 工具 | 参数 | 行为 |
|---|---|---|
| `start_scene` | kind, role, partnerName, goal | 创建场景（若本群已有 ACTIVE 场景则失败） |
| `wait_for_reply` | seconds (5..60) | 设 `waitUntil`，状态转 WAITING |
| `prompt_partner` | message | 引用自己上一条消息发出（被动回复，不耗主动额度） |
| `end_scene` | reason | 状态转 ENDED |

**工具可见性**：只在"当前群有 ACTIVE/WAITING 场景"或"最近 3 分钟有过场景"时，才把 `wait_for_reply / prompt_partner / end_scene` 发给模型；`start_scene` 常驻（但说明里写清"只有在明确要演一段时才调用"）。

## 四、判定链接入（关键改动）

`BotRuntime` 处理入站消息时，**在现有判定之前**插入场景查询：

```
1. 查本群 ACTIVE/WAITING 场景（按 groupId）
2. 若存在且我在参与者中：
   a. status == WAITING 且 now < waitUntil  → 忽略本条（不生成），记录 lastActivityAt
   b. isMyTurn(me)                          → 跳过 chime / 名字判定，直接生成
   c. 对方说话但没轮到我（expected 是别人）  → 走原判定链（可能插话）
3. 若存在但我不在参与者中：
   a. 对方场景正在演 → 人类/其他 bot 插话 → 注入"有人插话"信号，场景转 PAUSED（第一期用 WAITING 代替）
   b. 走原判定链
4. 无场景 → 完全走原判定链（行为与 2.12.0 一致）
```

**必须保证**：无场景时行为与 2.12.0 **逐字节一致**（默认 OFF）。

## 五、只读模式（OBSERVE）

新增配置 `sceneMode: OFF / OBSERVE / ACTIVE`，**默认 OFF**。

| 模式 | 行为 |
|---|---|
| OFF | 场景功能完全关闭，代码路径不进（与 2.12.0 一致） |
| **OBSERVE** | AI 仍会调用四个工具，但工具**只写 `scene_decisions` 表，不产生任何实际行为**（不等待、不催促、不结束）；判定链照旧 |
| ACTIVE | 工具真正执行 |

**OBSERVE 是第一期的主要交付形态**——先在真实群里跑几天，看 AI 判定的准确率，再决定是否切 ACTIVE。

调试页（`ChimeReviewScreen` 旁边加一个"场景"页签）显示：

- 当前群场景状态（kind / 轮次 / 等谁 / 剩余等待时间）
- 最近 20 条 scene_decisions（action / 参数 / 是否执行 / AI 给的理由）
- 一键切 OBSERVE / ACTIVE / OFF

## 六、数据库（18 → 19）

```sql
CREATE TABLE scenes (
  id INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  kind TEXT NOT NULL,
  groupId TEXT NOT NULL,
  participantsJson TEXT NOT NULL,
  goal TEXT NOT NULL,
  status TEXT NOT NULL,
  turnIndex INTEGER NOT NULL DEFAULT 0,
  expectedSpeakerId TEXT,
  waitUntil INTEGER,
  lastActivityAt INTEGER NOT NULL,
  createdAt INTEGER NOT NULL
)
CREATE INDEX index_scenes_group_status ON scenes(groupId, status)

CREATE TABLE scene_decisions (
  id INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  sceneId INTEGER,
  groupId TEXT NOT NULL,
  action TEXT NOT NULL,          -- START / WAIT / PROMPT / END
  argsJson TEXT,
  executed INTEGER NOT NULL,     -- 0=只读记录 1=实际执行
  reason TEXT,
  createdAt INTEGER NOT NULL
)
CREATE INDEX index_scene_decisions_group ON scene_decisions(groupId)
```

迁移注册进 `AppDatabase.create()`。`ConfigBackup` 只备份配置，不备份场景数据。

## 八、验收标准

### 自动检查

1. `:botcore:test` 全绿
2. `assembleRelease` 零错误、lint 零警告
3. 新增 `SceneTest` 覆盖：
   - `isMyTurn` / `roleOf` / `isExpired` 的边界
   - 场景已过期（> 10 分钟）→ 强制 ENDED
   - `waitUntil` 未到时忽略消息、到时不忽略
   - `sceneMode = OFF` 时工具不注册、判定链不查询（行为与 2.12.0 一致）

### 真机行为（OBSERVE 模式）

1. 群里正常聊天 2 小时 → `scene_decisions` 有记录，但**没有任何行为变化**（不出声、不等待）
2. 人工复盘：AI 调 `start_scene` 的时机是否合理（真的在发起一段对话），误判率 < 20%
3. 切换 OFF → 行为与 2.12.0 完全一致

### 真机行为（ACTIVE 模式，两个 bot）

1. 两个机器人配置好人设（一个逗哏、一个捧哏）→ 触发开场 → **连续对答 ≥ 8 轮**
2. 一方 25 秒不接 → 另一方发出催促，且催促后能接上
3. 连续 3 次催促无果 → 自动收尾，说一句得体的结束语
4. 人类插话 → 场景注入"有人插话"信号，不强制打断
5. 单场景不超过 10 分钟；单群每小时不超过 30 条

## 九、坑清单

1. **不能让协程挂起等待**：`wait_for_reply` 只写 `waitUntil` 时间戳，靠"下一条消息进来"或"定时 tick"检查，禁止 `delay(25000)`。
2. **`prompt_partner` 必须引用自己上一条消息**（带 `msg_id`），否则算主动消息，会被额度/开关拦住。
3. **动作说明要防滥用**：模型会"为了用工具而用工具"（每轮都 wait）。提示词里必须写"不要为了用动作而用动作"，并在代码里限制（同一场景相邻两轮不能连续 `wait_for_reply`）。
4. **两个 bot 的场景状态各自独立**（各自数据库）：这是设计，靠"双方看到同一条消息、用同一套判定"来对齐；不一致时的补救就是 `prompt_partner`。
5. **OBSERVE 的决策也必须落表**，否则无法复盘（这是第一期的主要价值）。
6. **人格设定由用户写**：代码不猜"谁是逗哏"。`start_scene` 的 `role` 参数由 AI 根据人格自行判断，判断错了由用户改人格，不在代码里硬编码。
7. **被动回复的 5 分钟窗口**：群聊被动消息"5 分钟内每条可回复 5 次"。场景内对方 5 分钟没说话时，`prompt_partner` 可能发不出去——必须捕获失败并转 ENDED，不能静默重试。
8. **不要在场景里跳过记忆/关系注入**：场景只改"要不要说话"，不改"以什么身份说话"。
